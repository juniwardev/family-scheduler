# Implement Brief: Fix Web Push VAPID signing (`Invalid PKCS8 input`)

## Symptom (verified in production, 2026-06-30)

A live `*/5` cron run fired the reminder engine. Email sent successfully (confirmed: a real reminder email arrived). Push failed with a deterministic crypto error:

```
"*/5 * * * *" @ 4:25:10 PM - Ok
  (error) push crypto error: DataError: Invalid PKCS8 input.
  (error) push crypto error: DataError: Invalid PKCS8 input.
  (log) [cron] materialize inserted=2 send={"sent":1,"failed":0,"transient":1}
```

A push subscription was registered just before this run (`POST /api/subscriptions - Ok`), so the failure is NOT a missing subscription. The engine found the subscription, tried to send, and the VAPID signing step threw. The failed push was classified `transient` and held for retry, but this is a deterministic code error, so every retry will fail identically until the code is fixed.

This is the `channels/push.ts` hand-rolled VAPID + WebCrypto path (Decision D2) running against a real push service for the first time. This is the single remaining blocker for push working for anyone.

## Goal

Web push is delivered to a real browser from the production deploy: the cron run logs a successful push send (no crypto error, `send.sent` includes the push), and an actual notification appears on the device.

## Root-cause hypothesis (confirm against the real code first)

The error `Invalid PKCS8 input` comes from `crypto.subtle.importKey('pkcs8', ...)`. VAPID keys generated by `web-push generate-vapid-keys` (which is what produced the keys in this project) are **raw base64url**, not PKCS8 DER:

- `VAPID_PUBLIC_KEY` is a 65-byte uncompressed P-256 point: `0x04 || X(32) || Y(32)`.
- `VAPID_PRIVATE_KEY` is a 32-byte raw scalar `d`.

So the code is almost certainly passing the base64url-decoded raw private scalar straight into `importKey('pkcs8', ...)`, which expects a full PKCS8 DER structure, not a bare 32-byte scalar. That mismatch is the error.

The Coder should confirm this by inspecting how `channels/push.ts` reads `VAPID_PRIVATE_KEY` and calls `importKey`, and by checking the actual format of the key stored in the secret.

## Likely fix (Coder confirms the exact approach)

Import the key in a format that matches the raw VAPID material. Two valid routes; prefer whichever is cleaner against the existing code:

1. **JWK import (usually simplest on Workers).** Build a JWK from the raw key material and import as `'jwk'`:
   - Split `VAPID_PUBLIC_KEY` (drop the leading `0x04`, then 32 bytes `x`, 32 bytes `y`).
   - Use `VAPID_PRIVATE_KEY` as `d`.
   - `importKey('jwk', { kty: 'EC', crv: 'P-256', d, x, y, ext: true }, { name: 'ECDSA', namedCurve: 'P-256' }, false, ['sign'])`.
2. **PKCS8 import.** Wrap the raw 32-byte scalar into a proper PKCS8 DER structure, then `importKey('pkcs8', der, ...)`.

Notes for whichever route is taken:
- VAPID JWT signing uses `ECDSA` / `SHA-256`. WebCrypto's `sign` already returns the raw `r||s` (JOSE) signature that the VAPID JWT needs, so no DER-to-JOSE conversion should be required. Do not add one unless a real test shows it is needed.
- Push has **two** crypto operations: VAPID auth signing (the one that threw here) and aes128gcm payload encryption (ECDH against the subscription's `p256dh`/`auth`). Only the VAPID signing error is in the log, but a full delivered push exercises both, so verify end-to-end delivery, not just that `importKey` stops throwing.
- Never log the private key or any key material.

## Secondary (optional, lower priority, only if quick)

The frontend appears to re-prompt for push permission on load rather than checking existing state. On startup it should call `registration.pushManager.getSubscription()` and only prompt/subscribe if there is no existing subscription, so a returning user is not asked again. This is a UX nicety, not a blocker, and is clearly secondary to the crypto fix. Do it in the same change only if it is small; otherwise note it as a follow-up.

## Tests / done conditions

1. **Regression test for key import + signing.** Add a unit test that imports a real test VAPID keypair using the chosen method and signs a sample VAPID JWT, asserting no error and a valid signature. This is the test that was missing and let the bug ship: it must exercise the actual crypto, not a mock.
2. **Local verification.** With `wrangler dev`, trigger the scheduled handler and confirm the push code path runs without the crypto error.
3. **Production verification (the real done-condition).** Deploy, create an event with a reminder a few minutes out, run `npx wrangler tail`, and confirm at the cron tick: no `push crypto error`, the send summary shows the push sent (not `transient`/`failed`), and a notification actually appears on at least a desktop browser. Confirm on an installed iPhone PWA as well if feasible (iOS push requires the standalone/home-screen install).
4. **Retry backlog.** Confirm the previously-stuck `transient` dispatch rows either send on the next run once the code is fixed, or are otherwise handled cleanly (no permanent stuck-retry loop). Consider whether a deterministic crypto failure should be classified `failed` rather than `transient` so a genuinely broken push does not retry forever; flag this as a question if it touches the engine's classification logic (which is otherwise locked).
