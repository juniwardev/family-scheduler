## 1. ✅ SHIPPED — `feat/fix-item-save` — Bug: partial items persist

> **Shipped 2026-06-30 in PR #2.** QA PASS (`docs/qa/fix-item-save-report.md`).
> **The framing below was wrong, and the plan corrected it:** the root cause was a *frontend*
> form-flow bug — the "Add reminder" button defaulted to `type="submit"`, so clicking it submitted
> the create form early. It was never a missing server-side validation gate, and the item was not
> being POSTed early to obtain an ID. See `docs/plans/fix-item-save.md` §3 for the evidence.

**Problem:** When creating an item, an incomplete item gets saved before the form is finished, and the user has to go back and edit it to fill in the rest. The partial item **persists** (it is written to the database), so this is a validation-gate defect, not a phantom autosave.

**Fix:** Enforce required-field validation on the create/save path so an item cannot be saved until its required fields are present. Because partial items currently persist, the gate must be server-side (in the API/`db.ts` create path), not only in the UI.

**Open design decision (architect decides and documents):** which fields are required to save, and whether the required set differs by item type (event vs task). Likely name + date/time required; location, notes, and reminders optional. The architect determines this per type and records it in the plan with a rationale.

**Done:** creating an item with a missing required field is rejected (server-side 400 and a clear UI message); a fully-filled item saves; no partial item can land in the database. Regression test covers the rejection.

**Process:** small, isolated. Architect writes a short plan (required-field decision), then Coder → QA. Own branch, own PR.

## 2. ✅ SHIPPED — `feat/notifications-and-location` — Richer notifications + smart location

> **Shipped 2026-07-11 in PR #6**, approved for deploy in `3546f0c`
> (`docs/qa/notifications-and-location.approved`). Type-aware subjects, item-timezone times,
> `?item=` deep links, and smart location (map link / "Tap to join" / plain text) are all live.
> Two live confirmations are still outstanding and tracked in
> `docs/qa/prod-verification-checklist.md`: eyeballing a real reminder email, and watching the
> daily-digest cron tick.

Two related, cross-layer improvements grouped because both concern how an item's details are presented (in-app and in notifications). This branch touches the notification path, which was just verified working, so it must be re-tested end-to-end after (wrangler tail at a live cron tick + a real device) to confirm delivery still works after enriching content.

### 2a. Notification content (email + push)

Current state is unusable to a human: subject `"Reminder: item due"`, body `"You have a reminder for item ID: <uuid>"`.

Target:
- **Subject:** type-aware plus the item name. E.g. `Event reminder: Alex football practice`, `Task due: Permission slip`.
- **Body:** item name, human-readable date/time rendered in the **item's stored timezone** (not epoch, not account-fixed), location (rendered per its type, see 2b), notes, and a **deep link that opens the specific item**.
- **Push:** same information compressed. Notification title = item name/type; body = time + location. Tapping the notification opens the specific item (service worker `notificationclick` → deep link).
- **Never** show the raw UUID.

Deep link mechanics: `APP_URL/?item=<id>` (or similar). Requires a small **frontend addition**: read the `item` param on load and open that item's detail view. Both the email link and the push `notificationclick` use the same deep link.

### 2b. Smart location handling

Location stays a free-text field (so "Home", "Alex's school", or a full address all work). The app **auto-detects** how to treat the string, with a toggle to override a wrong guess:
- **Plain text** ("Home") → displayed as-is, not linkable. Default when it's neither a URL nor address-like.
- **Address** → renders as a link that opens the device's default maps app (Apple Maps on iPhone, Google Maps elsewhere).
- **Meeting link** (Zoom / Teams / Google Meet URL) → renders as "Tap to join," opening the app if installed, else the browser (the meeting URL schemes handle that handoff).

Detection logic lives in one place and is used by both the in-app item view and the notification content (2a), so a meeting link is tappable in the email/push too.

**Done:** a real reminder email and push each show type-aware subject, full human-readable details, a working deep link to the item, and correctly-rendered location (map link vs "Tap to join" vs plain text); verified on a real device at a live cron tick; email delivery and push delivery both still confirmed working.

**Process:** architect plan → review → Coder → QA. QA's done-condition includes the live-device re-test, since this touches the just-fixed notification path.

- **NEW (2026-10-04) — Default the app to the Calendar view** (requested by Junior: "it's easier to see what's happening today, tomorrow, etc."). - **NEW (2026-10-04) — Places lookup so a venue name auto-fills its address** (requested by Junior: searching a clinic's name should return the address and populate the location field). **This is the first external paid API in the project — that, not the UI, is the work.** What already exists is classification and link-building, not lookup: `src/shared/location.ts` has `classifyLocation` (plain/address/meeting), `buildMapsUrl(query, provider)` with **search-query semantics**, `resolveMapsProvider` (NULL -> apple, Decision 6: owner's iPhone has no Google Maps app), the `items.location_kind` override column and the per-user `users.maps_provider` preference. **None of it resolves a name to an address** — `buildMapsUrl` hands a raw string to a maps site and lets *that* site search. **What a plan must settle:** (1) **provider** — Google Places and Apple MapKit JS authenticate differently (API key vs signed JWT), and the existing per-user `maps_provider` preference raises the question of whether lookup follows the user's provider or standardises on one; (2) **the key never touches the client** — this needs a new authorized Worker endpoint proxying the provider, plus the key as a **secret** (`wrangler secret put`), not a `[vars]` entry (and note [vars] mis-nesting has already bitten once — see the `preview_urls` row in the deployment history); (5) what gets stored — the display name, the formatted address, or both, and whether `location_kind` is then forced to `address` (the override rules in `resolveLocationRender` already make `address` always build a maps href); (6) offline/failure behaviour, since this is a PWA and the field must stay free-text typeable when lookup is unavailable. Own branch, architect plan -> review -> Coder -> QA. Biggest of the three.

- **✅ SHIPPED (2026-09-21) — Archived state for items** (requested by Junior). Landed in PR #26, live as `507ebcf1`, confirmed on the owner's iPhone and passed a live production smoke test (`docs/qa/item-archive-prod-smoke.md`). **(b) auto-archive was CUT** mid-review and is banked in `docs/plans/item-archive.md` Appendix A with its 30-day rule intact — re-decide before building it. Original request below, kept for history. Three capabilities: (a)
  **manually archive** an item once its date has passed; (b) **auto-archive on a schedule**;
  (c) **view archived items**, and **duplicate** one into a new item by changing title/date/location
  — "take an old item and use it to create a new one".

  **Three product decisions already made (2026-09-19), so a plan does not need to re-ask:**
  1. **Archived is a separate axis from completed**, not a replacement. A new `archived_at` column
     alongside `completed_at`. An item can be done-but-visible, archived-but-not-done (a past event,
     which never had a `completed_at` at all), or both. This is what makes "archive after the date
     passed" work for **events**, which have no completion concept.
  2. **Recurring items are excluded entirely** — manual and automatic. A series has no single
     "date passed" and may run forever; a repeating school run must not vanish because one
     occurrence went by. This also matches the existing precedent exactly: `completed_at` is
     **non-recurring only** (`migrations/0001_init.sql:30`), with recurring completion living in the
     separate `item_occurrence_state` table (`0002_occurrence_state.sql`).
  3. **Duplicate, not unarchive.** The archive is a historical record and never changes; duplicating
     copies an archived item into a new editable one. Chosen over "unarchive in place" because
     editing a past item into a future one destroys the record of what actually happened, and over
     "both" because the stated need is the duplicate.

  **Grounding gathered (2026-09-19), so a plan starts from facts rather than a survey:**
  - `items` (`migrations/0001_init.sql:18-34`) has no archive column today. Adding a nullable
    `archived_at INTEGER` is **additive** and therefore safe under `docs/runbooks/deploy.md`'s
    guarantee (existing rows get `NULL`; reads use `SELECT *` and map tolerantly).
  - Two crons already exist (`wrangler.toml:20`): `*/5 * * * *` (reminder send loop) and
    `0 14 * * *` (daily digest, ~07:00 Pacific). The daily one is the natural host for auto-archive
    — a new cron would be a third trigger for a once-a-day job.
  - Authorization must go through `db.ts`, not the routes (project `CLAUDE.md` convention), so
    archiving inherits the same list-visibility rules and the PR #19 HTTP-layer guards apply.

  **Open questions a plan must answer — none blocking, all genuine:**
  - **The auto-archive rule.** "N days after the date passed" — what is N, is it configurable, and
    does it key off `start_at` or `end_at`? Does it apply to *everything* past, or only completed
    tasks plus past events?
  - **Reminders on archived items** — an archived item must surely not fire reminders. Check the
    pending-dispatch interaction, and note **P2-N1** (cleanup pending dispatch rows before FK
    cascade deletes) is a hard requirement in this repo.
  - **Visibility surfaces.** Archived items presumably disappear from the list *and* the calendar
    grid — confirm, since `CalendarView` merges occurrences across all lists.
  - **Duplicate semantics.** Does it copy reminders? Attachments (R2 objects — copying is not free)?
    Does the copy land in the same list?
  - **Where archived items are viewed** — a filter on the existing list, or a separate surface?
